Uberblick / Guides

Your first ten minutes.

Local only, no hub, no account. You write one page that says what the product should do, connect the agent you already use, and watch it read that page before it answers. Then you change the page and ask again. The last step records a decision and finds it again by issue number. Every step names the result you should see; if you do not see it, stop there.

1. Create the workspace in your project

Terminal
$ cd ~/Projects/my-product
$ ub workspace create "My product"
created    My product (3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f, local)
wrote      ~/Projects/my-product/.uberblick.json
open it with: ub open
$ ub open
web        http://127.0.0.1:13379/
workspace  My product (local)

Ctrl-C to stop.

Run it in the checkout of the product the pages are about, not in a notes folder: the binding in .uberblick.json is what later lets an agent started in this directory find the same workspace. The editor opens with two starter pages pinned in the sidebar. Leave ub open running.

You should see: the editor in your browser with Welcome to Uberblick and How to Use It in the sidebar.

2. Write one rule

Create a page and give it a title that says what it is about, say Checkout: rules. Three sentences are enough, as long as they are rules and not tasks:

Checkout: rules
Guest checkout asks for an email address and nothing else.
We never ask for a phone number; delivery problems go to the email.
A guest can turn the order into an account afterwards from the confirmation page.

Pin the page in the sidebar. Pinned pages are where an agent that has never seen the workspace starts, so what you pin is what it reads first. This is the whole idea: product intent, written for a reader who arrives cold, not a plan for this week.

You should see: the page in the sidebar next to the two starter pages.

3. Connect the agent

Terminal · a second one, same directory
$ cd ~/Projects/my-product
$ ub mcp install claude
uberblick registered with claude

client     claude (project)
file       ~/Projects/my-product/.mcp.json
command    ub mcp serve
ran        claude mcp add --scope project uberblick -- ub mcp serve
workspace  follows ~/Projects/my-product/.uberblick.json

Restart running agents to pick this up.

For Codex, ub mcp install codex. The command runs the client's own installer and registers one server named uberblick that starts ub mcp serve in this directory; it writes no config file of its own. Then put the workspace section from Agents over MCP into your AGENTS.md or CLAUDE.md. Its first line is the one that matters today: start from the pinned pages when you do not know the project.

You should see: the client lists an MCP server called uberblick after a restart.

4. Ask, change the page, ask again

Prompt
Does our guest checkout ask for a phone number? Answer from the
workspace and name the page you read.

Watch the tool calls: get_sidebar, then get_doc on Checkout: rules. The answer is no, with the page's title and id. Nothing was pasted into the prompt; the agent went and read.

Now change the second sentence in the browser to A phone number is optional, for delivery notifications only. Ask the same question again in the same session.

You should see: the answer changes with the page, and the agent cites the same page. No restart, no re-indexing, no copy of the text anywhere else. That is the difference to a Markdown folder: the page is read at the moment of the question.

5. Record a decision and find it by issue

Open an issue in your repository for the phone number question, say my-org/my-product#1, then:

Prompt
We are not sure whether guest checkout should ask for a phone number.
Record this as a decision in the workspace, link my-org/my-product#1,
and propose: optional, delivery notifications only. Do not decide it.

The agent creates a decision record, kind decision, with the question as the title, its proposed answer and the reasoning, and the issue linked in the prose. The record is open: agents propose, people decide. In the browser the topic page shows the open record with an answer editor; approve it, and it is in force under your name and date.

Prompt · a fresh session
Call find_decisions for my-org/my-product#1 and tell me what is decided.

You should see: the record comes back with your name, the date and the answer in force. A new session that knows nothing about the conversation finds it by the issue number alone. That is what stops an agent from reopening a settled question next month.

What you have, and what comes next

One workspace file on disk, one binding in the project, one page an agent reads before it answers, and one decision it finds by issue. From here:

  • Your first workspace explains what the two commands put on disk and how to add a second workspace or remove one.
  • Product intent that agents read before they build is this exercise at the size of a real product: a design review becomes pages and decisions, and issues point at them.
  • Set up a hub when a second person or a second computer should see the pages.
  • ub-agents runs steps 4 and 5 for you from issue labels on GitHub, with a person on the loop. Optional; nothing above needs it.
