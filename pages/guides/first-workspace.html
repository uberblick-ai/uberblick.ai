Your first workspace.

Two commands give you a workspace. This guide is about what those commands actually do: the one file they create, what goes into it, how a directory is tied to it, and what to do when you want a second workspace or none. The Workspaces page explains the workspace as a unit; this page explains the machinery.

Create it

Terminal
$ cd ~/Projects/my-product
$ ub workspace create "My product"
created    My product (3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f, local)
wrote      ~/Projects/my-product/.uberblick.json
open it with: ub open
$ ub open
web        http://127.0.0.1:13379/
workspace  My product (local)

Ctrl-C to stop.

Run it in the directory of the project the workspace belongs to. Nothing talks to a server: no hub, no login, no account. The editor opens with two starter pages, Welcome to Uberblick and How to Use It, pinned in the sidebar. Replace them when the workspace becomes yours.

What is on disk now

Two things were written.

  1. One SQLite file, the workspace itself. ~/.local/share/uberblick/3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f.sqlite, named after the workspace id. Everything the workspace is lives in this one file: every document, every comment, the sidebar, tags, decision records, and the full edit history. Copy the file and you have copied the workspace. XDG_DATA_HOME moves the directory.
  2. One small binding in the project. .uberblick.json in the directory you ran the command in, holding the workspace id and the hub it syncs with. For a local workspace that is none.
.uberblick.json
{
  "workspaceId": "uberblick-3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f",
  "hubUrl": null
}

Commit the binding. Every terminal command, every MCP server and every agent that starts inside the directory looks upward for the nearest .uberblick.json and lands in the same workspace. There is no current workspace on the machine, only the one a directory points at. Two shell variables, UB_WORKSPACE_ID and UB_HUB_URL, override the file for one process; see Project binding.

A third directory, ~/.config/uberblick, appears the first time it is needed. It holds the computer's own signing secret, made along with the workspace so agents can sync with the local hub before the first ub open, and, once you sign in to a hub, the device credential. It is never part of a workspace.

What the file stores

The file is an ordinary SQLite database; sqlite3 opens it. Documents are not stored as text but as the history of changes that produced them, which is what lets two computers edit the same page offline and merge without a conflict screen.

TableWhat it holds
metaThe workspace name, the hub it syncs with, and the last full acknowledgement from that hub.
updates, snapshotsThe documents: every edit as a CRDT update, plus periodic snapshots so a page opens without replaying years of history.
pending_roomsChanges the hub has not acknowledged yet. This is the offline queue; it survives a restart and drains on reconnect.
doc_index, doc_tags, doc_linksTitles, descriptions and the full-text search index; tags; links between documents, for backlinks.
decision_github_refsThe GitHub issues and pull requests a decision record points at.

Only the first three tables are the workspace. The index tables are rebuilt from them. Back up the file while nothing is writing to it, or use the hub, which keeps a copy of everything anyway.

More than one

A workspace is a project's, not the machine's, so a second project gets a second workspace: run ub workspace create in its directory and a second SQLite file appears next to the first. Two projects can also share one workspace: copy the binding file, or run ub workspace use 3f0c2a1e with the id, or a unique prefix of it, of a workspace this machine already has.

Terminal
$ ub workspace list
* 3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f | My product       | local
  9b71d0c4-2e5f-4a8b-b3c6-1d2e3f4a5b6c | Acme product     | https://hub.example.com
$ ub status
workspace   My product (3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f)
hub         local, this computer only
version     client 0.4.8
account     none needed for a local workspace
chosen by   project config in ~/Projects/my-product
stored in   ~/.local/share/uberblick/3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f.sqlite
problems    none

ub workspace list is one row per copy on this computer, the one this directory uses marked. ub status says where that selection came from. ub workspace fork copies the bound workspace into a new file with a new id and binds the directory to the copy, which is how you try a restructuring nobody else sees.

Remove one

Terminal
$ ub workspace remove 3f0c
Delete this computer's copy of workspace 3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f? This is the only copy of this local-only workspace. [y/N] y
removed 3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f from this computer

Removal deletes this computer's file and nothing else. A workspace that lives on a hub is fetched again with ub workspace use and the link; a local-only workspace is gone, which is why the command asks. It refuses while this directory still uses the workspace or ub open serves it, so switch away and stop ub open first, and restart any agent that had the workspace open, because their MCP servers refuse to write to a removed workspace. The binding file stays; delete it or point it elsewhere.

How to grant others access

A local workspace has no members because it has no server. To share it, a hub holds the copy the others fetch, admits them as members, and passes changes between the computers. Set one up, then run ub workspace promote https://hub.example.com in the project: the file you have is uploaded as it is, with its id and history, and the binding switches to the shared copy. From then on your colleagues run ub workspace use with the link and get their own file under their own ~/.local/share/uberblick.
