Set up a hub.

A hub is the one piece of Uberblick that runs on a server. It keeps a copy of each shared workspace, admits members by their GitHub account, and passes changes between computers that each keep their own full copy. This guide takes a local workspace from Your first workspace to one a team edits, in six steps. The Run a hub page has the reference.

1. Pick a machine

Any Linux box with Docker Engine 28 or newer on x86_64, or a Mac with Docker Desktop for a hub that only your own computers use. A small virtual machine is plenty: the hub stores workspaces in SQLite and does no heavy work. Give it a name other computers can resolve. Tailscale is the easy answer for a team; a public host name with port 443 open works too.

2. Start the hub

Terminal
$ mkdir -p ~/uberblick-remote && cd ~/uberblick-remote
$ docker cp $(docker create --platform linux/amd64 ghcr.io/uberblick-ai/hub:0.4.7):/release/. .
$ cp remote.env.example .env
$ sh bin/remote-compose.sh up --detach

The release ships its own Compose files inside the hub image; the second line copies them out. The hub is now listening on http://localhost:8080 of that machine and nowhere else. Workspaces and the claim live in named Docker volumes, so restarts and updates keep them.

3. Claim it

Open http://localhost:8080 on that machine and choose Sign in with GitHub, or run ub auth login http://localhost:8080 from it. The first GitHub account that signs in becomes the hub's administrator. Nothing else can claim it afterwards, so do this before you open the hub to the network. Further hub admins are appointed on the host with ub-hub hub-admin add.

4. Make it reachable

Set one route in .env and recreate.

RouteIn .env
Tailscale, recommended (Linux)WEB_HOST=machine.tailnet.ts.net and TAILSCALE_IP from tailscale ip -4
A public host nameWEB_HOST=hub.example.com, with port 443 open
Terminal
$ sh bin/remote-compose.sh up --detach --force-recreate
$ sh bin/remote-compose.sh exec hub ub-hub status
release 0.4.7 · claimed by ben · https://hub.example.com

The hub serves TLS itself on the host name you gave it. Clients refuse an unencrypted hub unless it runs on the same machine, so there is no insecure mode to forget to turn off.

5. Upload the workspace you have

Terminal
$ cd ~/Projects/my-product
$ ub auth login https://hub.example.com
Open https://github.com/login/device and enter the code ABCD-1234
… signed in as ben
$ ub workspace promote https://hub.example.com
uploaded My product (3f0c2a1e-…), 14 documents, verified with a fresh client
wrote ./.uberblick.json: hubUrl https://hub.example.com

Back on your own computer. Promote uploads the local file as it is, same id, same history, archived pages included, then fetches it back as a fresh client to verify, and only then rewrites the binding. Interrupted? Run it again; it resumes. Commit the changed .uberblick.json so the repository points everyone at the shared copy. Starting from nothing instead? The hub comes with a default workspace; its id is shown after the claim.

6. Add people and connect their computers

Terminal
$ ub workspace member add dana --role member
grant dana (account 8213…) member of My product on hub.example.com? [y/N] y

Members are GitHub logins; there are no Uberblick accounts. A member reads and writes everything in the workspace, from the browser and over MCP, and a workspace admin also manages members. Then each person, on their computer, in the cloned repository:

Terminal
$ ub auth login https://hub.example.com
$ ub workspace use https://hub.example.com/3f0c2a1e-…
fetched 14 documents, verified, bound in ./.uberblick.json
$ ub open

Each computer now has its own SQLite file and works offline; the hub merges what comes back. Agents need nothing extra: an MCP server started in the directory uses the computer's login. A server that runs agents, such as an Actions runner, signs in once like any other computer and can be revoked on its own.

Keeping it running, backups and updates: Run a hub. Roles, devices and signing out: Access and membership.
