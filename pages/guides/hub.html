Set up a hub.

A hub is the one piece of Uberblick that runs on a server. It keeps a copy of each shared workspace, admits members by their GitHub account, and passes changes between computers that each keep their own full copy. This guide takes a local workspace from Your first workspace to one a team edits, in six steps. The Run a hub page has the reference.

1. Pick a machine

Any Linux box with Docker Engine 28 or newer on x86_64, or a Mac with Docker Desktop for a hub that only your own computers use. A small virtual machine is plenty: the hub stores workspaces in SQLite and does no heavy work. Give it a name other computers can resolve. Tailscale is the easy answer for a team; a public host name with port 443 open works too.

2. Start the hub

Terminal
$ mkdir -p ~/uberblick-remote && cd ~/uberblick-remote
$ for f in compose.yml remote.env.example remote.https.yml remote.tailscale.yml; do
    curl -fL -o $f https://github.com/uberblick-ai/uberblick-2/releases/download/hub-v0.4.8/$f
  done
$ cp remote.env.example .env && chmod 600 .env
$ docker compose config --quiet && docker compose up -d

Four files from one hub release and a private .env with HUB_VERSION set to that release; the latest release names it. The hub is now listening on http://localhost:8080 of that machine and nowhere else. Workspaces and the claim live in named Docker volumes, so restarts and updates keep them.

3. Claim it

Open http://localhost:8080 on that machine and choose Sign in with GitHub, or run ub auth login http://localhost:8080 from it. The first GitHub account that signs in claims the hub: it becomes hub admin and admin of the default workspace, and the login warns before the approval. Nothing else can claim it afterwards, so do this before you open the hub to the network. After the claim, login prints the ub workspace use command for the default workspace. Further hub admins are appointed on the host with docker compose exec hub ub-hub hub-admin add <github-login>.

4. Make it reachable

Set one route in .env and run docker compose up -d again.

RouteIn .env
Tailscale, recommended (Linux)WEB_HOST=machine.tailnet.ts.net and TAILSCALE_IP from tailscale ip -4
A public host nameWEB_HOST=hub.example.com, with port 443 open
Terminal
$ docker compose config --quiet && docker compose up -d
$ docker compose exec hub ub-hub status

The hub serves TLS itself on the host name you gave it. Clients refuse an unencrypted hub unless it runs on the same machine, so there is no insecure mode to forget to turn off.

5. Upload the workspace you have

Terminal
$ cd ~/Projects/my-product
$ ub auth login https://hub.example.com
hub        https://hub.example.com
open       https://github.com/login/device
code       WDJB-MJHT
waiting for approval…
signed in  octocat on https://hub.example.com
$ ub workspace promote https://hub.example.com
uploading  My product (3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f) to https://hub.example.com
verified   14 documents, including archived ones
promoted   My product (3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f, https://hub.example.com)
wrote      ~/Projects/my-product/.uberblick.json
share link: https://hub.example.com/3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f
commit .uberblick.json so teammates only need ub auth login

Back on your own computer. Promote uploads the local copy as it is, same id, same history, archived pages included, verifies the upload, and only then rewrites the binding. Interrupted? Run it again; it resumes. Commit the changed .uberblick.json so the repository points everyone at the shared copy. Starting from nothing instead? The hub comes with a default workspace; its id is shown after the claim.

6. Add people and connect their computers

Terminal
$ ub workspace member add dana
Grant access on https://hub.example.com to workspace 3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f for "dana" (GitHub account 480938) as member? [y/N] y
added "dana" (GitHub account 480938) as member

Members are GitHub logins; there are no Uberblick accounts. A member reads and writes everything in the workspace, from the browser and over MCP, and a workspace admin also manages members. Then each person, on their computer, in the cloned repository:

Terminal
$ ub auth login https://hub.example.com
$ ub workspace use https://hub.example.com/3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f
fetched    My product from https://hub.example.com: 14 documents, 1 archived
using      My product (3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f, https://hub.example.com)
wrote      ~/Projects/my-product/.uberblick.json
open it with: ub open
$ ub open

With the committed .uberblick.json in the clone, the middle command is not even needed: ub auth login reads the hub from the file. Each computer now has its own SQLite file and works offline; the hub merges what comes back. Agents need nothing extra: an MCP server started in the directory uses the computer's login. A server that runs agents, such as an Actions runner, signs in once like any other computer and can be revoked on its own.

Keeping it running, backups and updates: Run a hub. Roles: ub workspace member. Devices and signing out: ub auth.
