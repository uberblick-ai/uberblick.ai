Set up a hub.

A hub is the one piece of Uberblick that runs on a server. It keeps a copy of each shared workspace, admits members by their GitHub account, and passes changes between computers that each keep their own full copy. This guide takes a local workspace from Your first workspace to one a team edits, in five steps. The Run a hub page has the reference.

1. Pick a machine

Any Linux box with Docker Engine 28 or newer on x86_64, or a Mac with Docker Desktop for a hub that only your own computers use. A small virtual machine is plenty: the hub stores workspaces in SQLite and does no heavy work. Give it a name other computers can resolve. Tailscale is the easy answer for a team; a public host name with port 443 open works too.

2. Start the hub

On the hub machine from step 1, not on your own computer. Set HUB_HOST to the name the other computers will use: the machine's Tailscale name, such as machine.tailnet.ts.net, or a public host name with port 443 open. One line does the rest.

Terminal
$ HUB_HOST=hub.example.com /bin/bash -c "$(curl -fsSL https://uberblick.ai/setup-hub.sh)"
checked    curl, Docker Engine 28.3.1, Docker Compose 2.29.2, ports 8080 and 443 free
release    hub-v0.4.9, four files into ~/uberblick-remote
wrote      ~/uberblick-remote/.env (HUB_VERSION=0.4.9, WEB_HOST=hub.example.com)
started    hub healthy on https://hub.example.com
next       claim it from your own computer: ub auth login hub.example.com

The script checks Docker before it downloads anything, starts the newest hub release and waits until it is healthy. The hub serves TLS itself on that name. The same line run again later updates it. Variables, routes and the ub-hub commands are on Run a hub.

3. Claim it

Terminal
$ ub auth login hub.example.com
hub        https://hub.example.com
open       https://github.com/login/device
code       WDJB-MJHT
waiting for approval…
this hub has no admin yet; the account that approves becomes its admin
signed in  octocat on https://hub.example.com, hub admin
default workspace: ub workspace use https://hub.example.com/8a1f3c5e-2d4b-4e6f-9a0c-1b2d3e4f5a6b

From your own computer. The first GitHub account that signs in claims the hub: it becomes hub admin and admin of the default workspace, and the login warns before the approval. Nothing else can claim it afterwards, so do this right after the hub is up.

4. Upload the workspace you have

Terminal
$ cd ~/Projects/my-product
$ ub workspace promote hub.example.com
uploading  My product (3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f) to https://hub.example.com
verified   14 documents, including archived ones
promoted   My product (3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f, https://hub.example.com)
wrote      ~/Projects/my-product/.uberblick.json
share link: https://hub.example.com/3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f
commit .uberblick.json so teammates only need ub auth login

Still on your own computer, in the project directory, signed in since the claim. Promote uploads the local copy as it is, same id, same history, archived pages included, verifies the upload, and only then rewrites the binding. Interrupted? Run it again; it resumes. Commit the changed .uberblick.json so the repository points everyone at the shared copy. Starting from nothing instead? The hub comes with a default workspace; the claim printed its ub workspace use line.

5. Add people and connect their computers

Terminal
$ ub workspace member add dana
Grant access on https://hub.example.com to workspace 3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f for "dana" (GitHub account 480938) as member? [y/N] y
added "dana" (GitHub account 480938) as member

Also from your own computer, in the project directory: the command talks to the hub the directory is bound to, so nothing runs on the hub machine. Members are GitHub logins; there are no Uberblick accounts. A member reads and writes everything in the workspace, from the browser and over MCP, and a workspace admin also manages members. Then each person, on their computer, in the cloned repository:

Terminal
$ ub auth login https://hub.example.com
$ ub workspace use https://hub.example.com/3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f
fetched    My product from https://hub.example.com: 14 documents, 1 archived
using      My product (3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f, https://hub.example.com)
wrote      ~/Projects/my-product/.uberblick.json
open it with: ub open
$ ub open

With the committed .uberblick.json in the clone, the middle command is not even needed: ub auth login reads the hub from the file. Each computer now has its own SQLite file and works offline; the hub merges what comes back. Agents need nothing extra: an MCP server started in the directory uses the computer's login. A server that runs agents, such as an Actions runner, signs in once like any other computer and can be revoked on its own. An agent that runs elsewhere, in a cloud session or a hosted assistant, needs no ub at all: the hub serves the same MCP tools at https://hub.example.com/mcp/<workspace-id>; the person adds that URL to their client, signs in with GitHub in the browser, and the connection appears in their device list, where it is revoked like a computer.

Routes, ub-hub, endpoints and updates: Run a hub. Roles: ub workspace member. Devices and signing out: ub auth.
