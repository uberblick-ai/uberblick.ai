Moving our agent loops off the laptop

Ben · Building note

Since 26 October, CampfireFM's agent loops run on a dedicated server: the backend, a CRM prototype and, since this week, the studio app. Here's the setup, what broke, and what carries over to other teams.

Why a server

ub-agents runs a preparer, implementer, reviewer and integrator, steered by GitHub labels. A launcher claims queued work wherever it runs. On my laptop, closing the lid stopped it; evening issues waited until morning.

Uberblick's box provided a baseline: three manually started tmux launchers, 454 runs over 14 days, never more than two at once. We chose the same size for CampfireFM, starting with two loops and expecting more. Its runs are heavier, with a database, cache, object storage and search engine in containers. The server needed to start, restart and upgrade loops itself, and report when one stopped.

What the agents may not reach

Agents run code from pull requests with the launcher's environment and user rights. That determines the boundaries:

  • A dedicated, replaceable machine. A Hetzner VM with 8 shared vCPUs and 16 GB, recreated from Terraform and one setup script. Nothing irreplaceable lives there; a suspect box gets replaced.
  • No public ports or private network. Its VPN tag lets people in but reaches no peers. A canary alerts if it can reach staging. Cloud metadata is blocked for agents.
  • No privileged agent user. No sudo or docker group membership. Backend containers use that user's rootless Docker.
  • Only runtime credentials. The agents' GitHub token, a long-lived Claude Code token, and Codex and Uberblick hub device logins. No person's age key. The box has its own key; repositories choose which encrypted values it can open. So far, none.

systemd, with tmux inside

The documented service command is ub-agents launch --no-ui. We wanted the live queue, agents and activity view, which needs a terminal. Each systemd user unit therefore starts its launcher in a dedicated tmux server. A wrapper waits for the session and returns the launcher's exit status; attaching shows the live view.

A shared tmux server would belong to the first unit and die when that loop stopped. Separate servers keep loops independent. This is our choice, not a requirement: about a hundred lines of wrapper, plus a trap. Anyone attached can press q, draining the launcher to a clean exit.

The first week

  • 41 restarts in a day went unnoticed. On 30 October, deep in swap, a process-listing timeout made the CRM launcher exit every 30–45 minutes. systemd restarted it; it looked active all day. A start limit would have left it dead. Restarts now back off from one minute to thirty with no limit, and an alert counts them.
  • One build can take the box. That repository's builds and end-to-end tests reached 8.5 GB plus 7.5 GB of swap in one launcher. Each launcher now has a soft memory cap, slowing runaway builds before another loop takes the OOM kill. Containers need separate caps: rootless Docker starts them outside the launcher's unit. The backend also binds fixed ports, so it gets one launcher per box.
  • Temporary files can fill RAM. Uberblick's own 16 GB box held 3.2 GB in RAM-backed /tmp, mostly Playwright and TypeScript caches competing with builds. Check where temporary files and caches live, put them on disk, and bound retention.
  • An upgrade deleted the running version. Launchers keep their starting version; our updater drains and restarts them. Homebrew cleanup removed that version while two were still draining and needed its helpers. ub-agents now keeps a startup copy of its code.
  • Some tools never updated. Updates between runs only handle recognised installs. Codex's native install was skipped 48 times as unknown; gh from apt never updated.
  • Root ran a script agents could replace. Setup ran from /tmp. After a reboot cleared it, an agent could pre-create the path and substitute code from a pull request for root to run. Root now runs setup from a directory only root can write; setup refuses anything else. A review caught this; it was not an incident.
  • The token reached too far. A classic repo token opens every writable repository across organisations, dozens of unrelated ones for our account. The fix is a fine-grained token limited to the loop's repositories.

What we watch

“Unit failed” catches little when restarts keep a broken loop active. We alert on three restarts in three hours, an enabled loop idle for 15 minutes, a version still old twelve hours after upgrade, and failing ub-agents doctor checks: expired logins can fail every run while the launcher stays up. Root collects health so agents cannot falsify it. Unexpected services, crontab entries or SSH keys in the agent account also trigger an alert.

What carries over

Any service manager needs to restart on every unrequested exit with a growing delay, stop with a signal that releases the claim, and detect a loop that's up but not working. Restarting clean exits also recovers from an accidental q. Ours still lets those exits stand; fixing that is next.

Run launchers on a server is the reference, with settings for systemd, launchd and Docker Compose. This post is the story behind it.

Next

From the next release, ub-agents can upgrade and restart itself in place between runs, replacing our updater. Releases needing every launcher upgraded together still wait for us. An attachable view for a launcher running without one could replace tmux next. Until then, three loops run around the clock, and my laptop lid is mine again.
