Moving our agent loops off the laptop

2026-10-31 · Ben · Building note

Since 26 October, the agent loops that build CampfireFM run on a server of their own instead of on my laptop: the backend, a CRM prototype and, since this week, the studio app. This note says how we set it up, what went wrong in the first week, and which parts we would do the same way anywhere.

Why a server

Our loop is ub-agents: a preparer, an implementer, a reviewer and an integrator, steered by GitHub labels. A launcher claims the next item from the queue and runs the agent for it, wherever you start it. For weeks that was a terminal on my laptop. The loop stopped when the lid closed, and issues labelled in the evening waited for the morning.

Uberblick's own loops already ran on a small box, three launchers in tmux panes that someone starts by hand. CampfireFM needed more than that. Its runs are heavier, they start a database, a cache, object storage and a search engine in containers, and there would be two loops from the start, with more to follow. So we built a box that starts its loops on its own, restarts them, upgrades them and tells us when one stops.

What the agents may not reach

Agents run code from pull requests, with the launcher's environment and its user's rights. Most of the design follows from that one sentence.

  • A machine of its own. A Hetzner VM with 8 shared vCPUs and 16 GB, built from Terraform and one setup script. It holds nothing we can't recreate, so a box we doubt gets replaced, not cleaned.
  • No way in, no way out. No public ports and no private network. It joins our VPN with a tag that people may reach and that reaches nothing, and a canary alerts if the box can ever connect to staging. The cloud metadata service is blocked for the agents.
  • An agent user without privileges. No sudo, and not in the docker group. The backend's compose stack runs on that user's own rootless Docker.
  • Only the runtimes' credentials. A GitHub token for the agents' account, a long-lived Claude Code token, and the device logins for Codex and the Uberblick hub. No person's key to our encrypted secrets is on the box. It has an age key of its own, and a repository decides value by value what that key may open. So far that is nothing.

systemd, with tmux inside

The documented way to run a launcher as a service is ub-agents launch --no-ui under a service manager. We wanted to keep the live terminal view, which shows the queue, the running agents and what each one is doing. It needs a terminal, and a service has none.

So each loop is a systemd user unit that starts its launcher inside a tmux server of its own, and a small wrapper waits for the session and passes the launcher's exit status back to systemd. Attaching shows the view, live. One tmux server per loop matters: a tmux server belongs to the unit that started it, so a shared one would stop with whichever loop stopped first.

This is our opinion, not a requirement. It costs about a hundred lines of wrapper, and it adds a trap: whoever attaches can press q, which drains the launcher until it exits cleanly.

The first week

Most of what we learned came from the box doing something we had not planned for.

  • 41 restarts in a day, and nobody noticed. On 30 October the CRM prototype's launcher exited every 30 to 45 minutes, because a process listing timed out while the box was deep in swap. systemd restarted it each time, and the unit looked active all day. Had systemd's usual start limit tripped, the loop would have stayed dead until someone looked. Restarts now back off from one minute to thirty with no limit, and an alert counts them.
  • One build can take the box. That repository's builds and end-to-end tests reached 8.5 GB plus 7.5 GB of swap in a single launcher. Each launcher now has a soft memory cap, so a runaway build slows down instead of an OOM kill landing in another loop. The containers needed a cap of their own: rootless Docker starts them outside the launcher's unit, where its cap doesn't reach.
  • An upgrade deleted the running version. A launcher keeps the version it started with, so our updater drains each loop and starts it again. Homebrew's cleanup removed the old version while two launchers were still draining on it, and a draining launcher still starts helpers from its own install. ub-agents now keeps a copy of its own code from startup, so a cleanup no longer matters.
  • Some tools never updated. ub-agents keeps the agent CLIs current between runs, but only installs it recognises. Codex from its own installer was skipped 48 times as an unknown installation, and gh from apt not at all.
  • The token reached too far. We started with a classic GitHub token, and repo opens every repository the account can write to, in every organisation, dozens of unrelated ones in our case. The fix is a fine-grained token for the loop's repositories and nothing else.

What we watch

"Unit failed" turned out to catch almost nothing. The alerts that matter are the ones the service manager doesn't show: a launcher restarted three times in three hours, an enabled loop that hasn't run for 15 minutes, a launcher still on an old version twelve hours after an upgrade, and a failing ub-agents doctor, because a launcher stays up while every run fails on an expired login. Health is collected as root, so nothing an agent changes can make a broken loop look healthy. One more alert fires when the agent user has a service, a crontab entry or an SSH key that setup didn't install.

What carries over

Very little of this is about systemd, tmux or Hetzner. Each fix answers a requirement any service manager has to meet: restart on every exit with a growing delay, stop with a signal that releases the claim, and watch for the loop that is up but not working. Writing those down changed our own setup too. A service that restarts on every exit it didn't ask for also starts a loop again after an accidental q, which makes the trap above harmless.

We wrote the requirements up as Run launchers on a server on the ub-agents site, with the settings that matter for systemd, launchd and Docker Compose. It is the reference; this note is the story behind it.

Next

Our updater is already gone. ub-agents now upgrades and restarts itself between runs, in place, and leaves a release that needs every launcher upgraded together to us. The next piece would be a view that attaches to a launcher running without one, which would replace tmux. Until then, the box runs three loops around the clock, and my laptop lid is mine again.
