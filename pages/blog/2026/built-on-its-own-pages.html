Built on its own pages, stage 1: read before you write

2026-10-22 · Ben · Building note

Uberblick is built by the loop it is made for: issues on GitHub, agents in four roles, and a workspace of pages that say what the product should do. This is the first of three notes on how that goes. The question for this one: can an agent be made to read the product's intent before it changes the product?

How we ran it

  • The pages. Fifty pages in one workspace: a product principles page, the CLI's intent per command, the MCP server's contracts, the "Web UI:" design pages, and the decision topics. Six of them carry the guidance tag.
  • The loop. ub-agents on GitHub Actions, four roles in a few lines of YAML, steered by labels: needs-preparation, ready, needs-review, ready-to-merge. Any agent runtime; we run Claude Code and Codex side by side.
  • The rule. The MCP server names the guidance pages when an agent connects and asks it to read the ones that apply before its first write. The agents' instructions add four lines: start from the sidebar, cite by id, call find_decisions for your issue, update the page in the pull request.
  • The person. I read the issue the preparer wrote, approve or reject the decisions agents propose, and read the corpus update in each pull request. I do not read most of the code.

What held

Every agent handled the refusal without instruction; the error names the pages, and reading them is one call each. No pull request in the period changed a behaviour a decision record had settled. The corpus update in the pull request turned out to be the strongest part of the loop: it is where a reviewer, human or agent, notices that the page and the code disagree, and in most of those cases the page was right.

Where it went wrong

  • The shared database. Every checkout on a machine uses the same workspace copy. An agent running branch code with a newer migration migrated my real workspace, and main then logged a compaction failure on every start. No data was lost; it was loud and it took a day to find. The fix is an issue, not a page.
  • Reading is not understanding. One implementer read the typography page, as required, and then built a monospace table header anyway. The reviewer caught it against the page. The server can guarantee the page was in the context; it cannot guarantee it was used. That is what the reviewer role is for, and it earned its keep.
  • Pages ahead of the code. A page may describe intended behaviour that has not shipped. Twice an agent treated an intended behaviour as a bug in the code and "fixed" it in the wrong direction. The rule now reads: pages describe intent; never make the page say less than it did because the code does less.

Next

Stage 2 is about decisions: whether a record written by an agent and approved by a person keeps a question closed across the runs that follow, and what the history looks like after a month. Stage 3 is the one we are least sure of: the loop proposing changes to its own rules from retrospectives, with a person deciding each one. Nothing changes automatically from a retro; that is the rule we will test hardest.

If you want to try the first stage on your own repository: install, tag three pages as guidance, and put the lines from Agents over MCP into your agent's instructions. Then read the corpus update in the first pull request.
