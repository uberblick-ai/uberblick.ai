Built on its own pages: how we're building Uberblick with Uberblick

2026-10-23 · Ben · Building note

We are starting a series on how we build Uberblick with Uberblick. Not because the product is finished, but because the way it is built is the point: issues on GitHub, agents in four roles, a workspace of pages that say what the product should do, and one person on the loop. This first note says where that came from, what three weeks of it produced, and what we learned.

Where this started

Uberblick was not the goal. The goal was proper loop engineering for our main product, CampfireFM, a native iOS and Android app with a Python backend. We wanted a loop that takes an issue and delivers a merged pull request without a person in the middle.

The hard part turned out not to be the agents. It was us. For a fully autonomous loop we had to get much better at describing what we want, and at coordinating between designers, product managers, engineers and agents. The pages we wrote for each other were not good enough for an agent to work from, and the decisions we had taken lived in chats and in heads.

So besides Uberblick, the knowledge base for humans and agents alike, we started ub-agents as the autonomous loop that reads it.

Three weeks, one engineer

The loop started around the beginning of October. Three weeks later, with mainly one engineer working on all of this, we are pretty close to autonomy. Almost everything you see here was built by that loop: the editor, the CLI, the MCP server, the hub, this website.

The loop is ub-agents on GitHub Actions: four roles in a few lines of YAML, steered by labels. A preparer writes scope and criteria into the issue, an implementer codes and opens the pull request, a reviewer reviews the exact head, an integrator merges. We run Claude Code and Codex side by side. Every run has the agent's local copy of the Uberblick workspace available through the MCP server, so the pages are within reach whether or not someone pasted them into the issue.

Autonomy, day by day

Autonomous follows the delivery report's definition: the integrator merged the delivery with no wasted run, no stop and no notice that a person had to act. A reviewer sending the work back still counts; a wasted run does not. Stops are counted separately, as events. A day with five deliveries swings the line. By week it reads 29% (1 to 4 October), 45%, 54% and 74% (19 to 21 October).

Retros, and autonomy rising slowly

It was clear that the first runs would have errors, and they did. Branch code migrated the shared workspace copy, reviewers checked commits that had moved on, runs waited a quarter of an hour for a runner to install its libraries. That is why we added retrospectives to the loop. When a run lost something real, the agent posts one short paragraph: the cost, the cause, and the smallest change that would have prevented it. Two from the implementer, as the agent wrote them.

On the Hocuspocus upgrade the preparation had missed a second change in the upstream release, how the library rejects a login, because headless runs could not read the package registry and had guessed instead. The agent stopped and sent the issue back. The retro:

The Hocuspocus upgrade needs another preparation pass because the scope covered awareness removal but missed the close-then-throw authentication-refusal change in the same upstream lifecycle update. The implementation is retained, but handoff stopped at that contract gap. Checking late refusal delivery through the composed admission suite during dependency characterization would have exposed the scope choice before implementation.

On 21 October a change to the loop's permissions let preparers read the registry and the release notes before writing the contract.

On #1062 two parts of the UI shared a text colour. A fix that was right for one would have nearly hidden the other's controls, so the agent threw its own prototype away and sent the issue back. The retro:

The rendered verification for #1062 found a contract gap after a panel utility prototype had begun: enabled code-copy text uses shared muted ink at 60% opacity, while terminal controls use that same ink over a fixed dark sibling screen. The token-only fix for the first nearly hides the second, so the run returned the issue and discarded its prototype. For future shared-ink changes, preparation should include the rendered consumers' opacity and overlapping grounds when bounding scope; ancestor-only token ratios missed the necessary fixed-ground consumer correction here.

Nobody reads every retro by hand. A skill evaluates the day's deliveries and retros every morning and files issues to improve the loop; a person decides each one. More on that in a later note.

Then we saw a slight increase in autonomy. Not because the models changed in those weeks, but because we got better at describing the issues, and because the documents and the decision records the agents read got better with every retro.

What we learned

  • Learn from each run. Keep every run headless. When a run lost something real, let the agent write down the cost, the cause and what would have prevented it. Those short reports are what we learn from; nobody sits and watches a run.
  • Always fix the guidance and the structure, never the issue. When a run goes wrong, the fix is the Uberblick page, a gate or an adjusted instruction. Fixing the issue at hand teaches the loop nothing.
  • Learn how to cut issues, and work on good issue templates. A recurring cause of wasted runs was an issue that was too big, or that left out what the agent had to read first.
  • Clear gates and agent definitions help a lot. Look at how often ours changed: the implementer's definition alone has 52 commits since the end of August, 26 of them in October. Our job was to observe and adjust, a bit like a kindergarten teacher watching a toddler learn to walk: add a guardrail where it struggles, then step back.
  • Trust the loop. Do not jump in when it gets frustrating. Revert, restart the issue or the pull request, and see whether your structural change improves the outcome.
  • Build skills and share them with the team. We have our own skills page at CampfireFM, like skills.uberblick.ai.
