Letting agents auto-merge Dependabot pull requests

2026-10-28 · Ben · Building note

Since 22 October, the agent loop that builds Uberblick also merges its Dependabot pull requests, with no person in between. This note says why we wanted that, what we changed to get there, and what still comes to us.

Why bother

A dependency update is the dullest pull request there is, and also the one that most often sits. It needs no design and no discussion, so it never feels urgent, until the one in the pile is a security fix. Dependabot's automatic security updates open that pull request on their own as soon as an advisory reaches GitHub. The slow part is the merge.

The last two weeks made that plain. On 14 October Next.js shipped two critical unauthenticated remote code execution fixes in 16.4.1 and 15.5.28. One of them sits in an image library, so for many projects the fix is a lockfile bump of sharp. A week later PHP released PHP2Shell, CVE-2026-109618 and CVE-2026-109619, found with the help of AI models. Amazon saw an exploitation attempt on 17 October, four days before the flaws were disclosed, and wrote that "AI-assisted analysis makes it cheaper to turn a patch diff or advisory into a working exploit." By the weekend TechCrunch called it the PHP-ocalypse, and sites from Wikimedia to the Internet Archive had gone offline for a while to patch.

When a patch can be turned into an exploit in days, and sometimes the exploit comes first, a security update that waits for someone to have a quiet afternoon waits too long. We wanted those to merge as soon as CI is green, and we wanted a person only where judgement is actually needed.

Before

The usual way to auto-merge Dependabot is a GitHub Actions workflow: read the update type with dependabot/fetch-metadata, and turn on auto-merge for patch versions. That merges whatever passes CI and stops at the first red check. We wanted something that reads the diff, knows our rules and can fix a broken test, so we gave the job to the agents that already merge everything else.

Our loop is ub-agents: a preparer, an implementer, a reviewer and an integrator, steered by GitHub labels. Until 22 October it treated dependabot[bot] like any outside author, and rightly so. An outside pull request needs a maintainer to start it and to approve each new head before an agent runs it. Dependabot rebases often, and every rebase makes a new head.

So the last four Dependabot pull requests before the change, #1365, #1834, #1982 and #1983, all needed me. Some stalled twice, once because the Cloudflare preview bot edited its own comment and the loop counted that as new outside feedback. A vite security fix, #2027, sat for a day untouched.

Three settings

The change is small. Dependabot's own default label, dependencies, starts the integrator. Dependabot becomes a trusted pull request author, so it needs no start and no head approval. The preview bot's comment no longer counts as outside feedback.

ub-agents.yaml
# Dependabot PRs need no maintainer start or head approval, and their
# bodies (upstream release notes) never reach agents.
trusted-pr-authors: [dependabot]

# The preview comment neither suspends a PR nor marks it as outside input.
trusted-bots: [cloudflare-workers-and-pages]

agents:
  integrator:
    # Dependabot labels its PRs `dependencies`, which sends them straight here.
    trigger: [ready-to-merge, dependencies]

Trust here is narrow. The body of a Dependabot pull request pastes the release notes of the package, and anyone who publishes a package writes those. An agent that reads them can be steered by them. So the body never reaches an agent. The title and the diff are the whole stated intent: these packages move to these versions, and nothing else changes.

Our dependabot.yml groups the updates, one pull request for all security fixes and one weekly for minor and patch versions. Version updates wait seven days after a release, so a compromised publish has time to be caught. Security updates never wait.

What the integrator does

The rules live in our delivery policy, where the integrator reads them on every run:

  • Check the intent. The diff touches only manifests, the lockfile and the pinned versions of workflow actions, and it matches the title. A diff like that owes no agent review.
  • Check the gates. The required CI checks pass at the head, and the merged tree against today's main passes too.
  • Merge minor and patch, write a report. Every merge leaves a comment that says what was checked and why it was safe.
  • One repair round. When CI fails, the implementer gets one try to adapt. Its commit then owes a normal agent review. A second failure goes to a person.

From the run records on each pull request. #2027 shows my account as the merger because that run happened on the launcher on my laptop.

The first two were the easy kind, and the merge reports show what easy still includes. On #2027 a WebKit setup step hung for half an hour; the integrator saw the same hang on main, re-ran it once and merged. On #2143 it checked that the new pinned commit really is the upstream tag v5.2.1, and since main moved during the run, it tested the merge against both versions of main.

#2249 is the one we like best. The zod update broke a test: zod 4.6.6 writes nullable fields in the advertised MCP schemas as a type list instead of anyOf. The integrator found the failing test, confirmed it passes on main, and sent it back with the cause. The implementer changed two assertions and no production code. Because the pull request now had a commit that was not Dependabot's, the reviewer ran, and it checked every output schema under both zod versions: 56 fields spelled differently, same meaning. Then the integrator merged. Four runs, two models, no person, 37 minutes.

Uberblick exists to make the way we build our main product, CampfireFM, work better. So once we had seen this work in Uberblick, we adopted it for the CampfireFM backend too, on its own loop host. The first merge there took 12 minutes: on 27 October Dependabot opened a one-line workflow update at 21:25, the integrator picked it up 36 seconds later, waited for CI and merged it at 21:37.

Four is not a big number yet. Dependabot opens only a few pull requests a week for us, and that is the point: none of them takes a minute of our day now.

What still comes to us

  • Major versions, including a 0.x minor and a group with one major in it. TypeScript 7 and vitest 5 both needed code changes and a decision, and they would again.
  • Pinned packages. Our CRDT libraries, the collaboration server and the MCP SDK are pinned on purpose and ignored by Dependabot. Bumping one is a reviewed change.
  • Sensitive areas. An update that changes auth, sync, persistence or protocol behaviour escalates, whatever its version number says.
  • A second failure, or a fix that needs a real decision rather than adapting a test.

And Dependabot only sees what a manifest pins. The PHP interpreter in a server image or the runtime on a host is still somebody's job to update.

All of this is opinionated, and none of it is built into the loop. What goes to a person and what merges on its own comes from the agent instructions and the gates we chose. We found these to be sensible defaults, and changing one is an edit to a text file.

If you want this

You need a loop that can tell who authored a pull request, keep a bot's text away from the model, and follow written rules about what it may merge. Ours is ub-agents, and the three settings above are all it took on the loop's side. The rules are plain text in our repository; copy them and change what does not fit.
