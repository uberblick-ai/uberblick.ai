A monitor, not an app

Ben · Design note

Since 0.5.1, ub-agents monitor shows our agent loops on every machine in one browser page: what waits for a person, what runs, and what finished today. We could have built a desktop app for it. We chose not to, because the memory on our laptops belongs to the agents.

Why we needed one

The terminal view of ub-agents shows the runs of the launcher it belongs to. That was enough while every loop ran on a laptop. Then our loops moved to a server, and work started happening where nobody was looking.

One day we labelled an issue as ready at 11:13. At 11:22 the server claimed it, and nothing told us; we noticed by chance. Later that day another issue went through preparation, implementation, review and merge on the server in about an hour, and we followed every step by refreshing GitHub. The loop worked. We just couldn't see it.

The memory belongs to the agents

The obvious answer is a desktop app with a dashboard. Built on Electron, as so many are, it brings another copy of Chromium and Node, running all day to show a list that changes a few times an hour.

On a laptop that runs a launcher, that memory is already spoken for. The agents build, run test suites, start browsers for end-to-end tests and bring up databases in containers. On our server, one repository's build and tests reached 8.5 GB plus swap on their own. Whatever a dashboard holds is memory a build doesn't get.

So the monitor is a tab in the browser you already have open, served by a small process on your machine. We measured it on Linux while it served Uberblick's last 24 hours, 16 finished runs and three items waiting for us. The server held 28 MB idle and 35 MB after reading. The page's own JavaScript held about 1.5 MB. The whole tab, in the same Chromium, took 30 to 40 MB more than a nearly empty page.

What waits for you comes first

Before it went into ub-agents, the monitor was a single HTML page and a short script in CampfireFM's studio repository. The shape stayed: one page, read from the top, with what needs us first.

Needs human lists every item an agent handed back, with what it asks: the actions, and the options with the recommended one first. Below it, Running shows each live run with its agent and machine, Expired without a result shows runs whose launcher went away, and Recent activity shows the last 24 hours with result, duration, tokens and cost. If you want, the page notifies you, but only for what you choose. By default that's an item that newly needs a person.

From waiting to unblocked

Seeing that something waits is half the job. The other half is deciding, and that usually takes a conversation: what did the agent find, is its recommendation sound, what happens if we pick the other option?

Each item has a discuss with Claude button, and it saves you the part where you explain the problem. It opens Claude Code in the Claude app, already in your checkout, with the request to unblock that item through the ub-agents-unblock skill written out. You confirm the folder and send it.

You don't start from scratch. Claude gathers the context itself: how your loop is set up, the agent's notice, its outcome record with the options and the evidence behind them, and the item. Its first answer tells you in plain words what the decision unblocks and what the agent recommends. You don't paste links or retell the history; you go straight to the decision. Once you've made it, Claude resumes the item the way the notice says, and the loop picks it up again.

Nothing lives in the monitor

We describe ub-agents as making coding-agent work repeatable, inspectable and recoverable. The monitor holds to that by keeping nothing of its own. Every row on the page is a record the launchers already write to GitHub, read with the same rules the launchers use, and every row links to it. The page never changes anything on GitHub. Close it and nothing is lost; open it on another laptop and it shows the same loop.

It's light on GitHub too. It asks every 30 seconds, and because GitHub doesn't count a "304 Not Modified" answer, a quiet poll costs about one call from your hourly budget. The status bar shows how much of that budget is left.

Small on purpose

The monitor added no dependency to ub-agents. It's one HTML file of 26 KB and Python's built-in web server, listening only on your own machine. It reads GitHub with the login you already gave gh, and that login stays in the server; the page only ever sees the records it shows.

It's still marked experimental. If you run ub-agents, start it with ub-agents monitor and tell us what you miss. We'll keep it small.
