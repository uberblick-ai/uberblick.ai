Uberblick / Docs / CLI reference

ub workspace

A workspace is one set of documents, kept in full on every computer that uses it. ub workspace creates one, binds a project directory to it, fetches a shared one from a hub, publishes a local one, and manages members. A bare ub workspace prints this help and does nothing.

Usage

help
usage: ub workspace [command]

commands:
  create <name>               create and select a separate local-only workspace
  fork                        copy this workspace independently and select the copy
  promote <hub>               upload, verify and connect this local workspace
  member <command>            grant workspace access and manage members
  list [--json]               workspaces this machine has a database for
  use <link|id>               fetch a shared workspace or select a local replica
  remove <id|prefix> [--yes]  delete this computer's copy of a workspace

create

Terminal
$ ub workspace create "Acme product"
created Acme product (3f9c…) with starter documents
bound ./.uberblick.json to it

A local-only workspace with two starter pages, selected in this directory's .uberblick.json. No hub, no login. What lands on disk is on Your first workspace.

use

Terminal
$ ub workspace use https://hub.example.com/3f9c0a1e-…
$ ub workspace use 3f9c

Binds the project to a workspace, writing the nearest .uberblick.json or creating one here. A hub link has the workspace id as its last segment; a browser document address is not a workspace link. An id, a decorated slug-uuid or a unique prefix selects a workspace this machine already has. A shared workspace is fetched in full and verified before the binding is written; two workspaces are never merged. Needs a login for a hub workspace, and says so instead of starting one.

list

Terminal
$ ub workspace list
3f9c0a1e-…  Acme product        hub.example.com  (current)
8b2d4c77-…  Design notes        local

Every workspace this machine has a database for, with the one in force marked and the hub it was recorded from, or local. Reads the local replicas only. --json for scripts.

fork and promote

Terminal
$ ub workspace fork
$ ub workspace promote https://hub.example.com

fork copies this project's workspace into an independent local one with a new id and the same documents, and selects the copy; the source is untouched. promote uploads a local-only workspace to a hub, verifies the upload with a fresh client and only then binds the project to the hub copy. It needs a prior ub auth login to that hub, and the account must be a hub admin; rerun it after an interruption and it resumes. A workspace already on a hub cannot be promoted.

member

Terminal
$ ub workspace member add dana --role member
$ ub workspace member list
grant dana (account 8213…) member of Acme product on hub.example.com? [y/N] y
ben    1024…  admin
dana   8213…  member

Access to a shared workspace, as a workspace admin. Members are GitHub accounts; there are no Uberblick accounts. add resolves a GitHub login at the hub and asks for confirmation, --yes confirms without a terminal. role switches between member and admin; remove ends access on every device. The last admin cannot be demoted or removed.

Two roles in a workspace: a member reads and writes every document, from the browser and over MCP; an admin also manages members and the workspace settings. Reading and writing are not separate rights. A third role lives on the hub: the hub admin sees every workspace on it, suspends and restores them, and is the only one who can promote a new workspace onto it. The first account to sign in on a fresh hub claims that role; the operator appoints more with ub-hub hub-admin add, see Run a hub.

remove

Terminal
$ ub workspace remove 8b2d --yes

Deletes this computer's copy of one workspace and nothing else: bindings, logins and other workspaces stay. A workspace on a hub can be fetched again with use; local changes the hub has not acknowledged are lost. For a local-only workspace this may be the only copy. Switch away first and stop any ub open serving it.

Scenarios

Start alone, share later
create today, work locally, then promote to a hub when a second person arrives. The id and the history stay the same.
Two projects, one workspace
Run use in each project directory with the same id. Both bindings point at the one local copy.
Try something without touching the shared workspace
fork, experiment, and either promote the fork or remove it.
Someone leaves
member remove ends their access on every device. Documents already on their disk stay there; revocation cannot reach into a computer.
