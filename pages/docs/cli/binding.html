Uberblick / Docs / CLI reference

Project binding

A project picks its workspace with a .uberblick.json file. Every ub command that needs a workspace, and every agent started in the project, uses it. There is no current workspace on the machine, only the one a directory points at.

What the file holds

.uberblick.json · on a hub
{
  "workspaceId": "uberblick-3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f",
  "hubUrl": "wss://hub.example.com/ws"
}
.uberblick.json · local
{
  "workspaceId": "uberblick-9b71d0c4-2e5f-4a8b-b3c6-1d2e3f4a5b6c",
  "hubUrl": null
}

Two fields: workspaceId, and hubUrl, which is null for a local workspace. ub searches from the current directory up for the nearest file owned by you; one owned by another user is skipped and the search continues in the parent. Without a usable binding a command says so and stops. A binding selects a workspace; it cannot move this computer's copy to another hub. When a binding names a hub other than the one this computer recorded for the workspace, commands refuse and ub status reports the mismatch and the command that restores the selection.

Commands that write it

CommandWrites
ub workspace createA new file in the current directory
ub workspace useThe nearest existing file you own, or a new one in the current directory
ub workspace forkThe completed local copy, in the nearest file you own or a new one here
ub workspace promoteThe hub, in the nearest file you own; the workspace stays the same

Each prints the path it wrote. The ones that switch the workspace also print the previous one and the command that switches back; ub workspace has the outputs.

Committing it

Terminal
$ git add .uberblick.json && git commit -m "Use the shared Uberblick workspace"
# a teammate
$ git clone https://github.com/acme/notes && cd notes
$ ub auth login
$ ub open

Commit the file after promoting. Teammates who clone the project then only need ub auth login, which reads the hub from the file, and every agent that runs in the checkout lands in the same workspace. The file holds no secrets. Do not commit a file that binds to a local-only workspace; nobody else can reach it.

Environment overrides

Terminal
$ UB_WORKSPACE_ID=9b71d0c4-2e5f-4a8b-b3c6-1d2e3f4a5b6c ub status
$ UB_WORKSPACE_ID=3f0c2a1e-7b4d-4c2a-9e1f-5a6b7c8d9e0f \
  UB_HUB_URL=wss://hub.example.com/ws ub status   # first time on this machine
  • UB_WORKSPACE_ID overrides the file for one shell session or one MCP entry. Alone, it uses that workspace with the hub this computer already knows for it, or local. The uberblick- prefix is optional.
  • Add UB_HUB_URL, a hub address or local, only for a workspace this computer does not have yet; without it the command stops and says so. It cannot replace this computer's record of a workspace's hub.
  • UB_HUB_URL alone, or empty, is an error.

A hub on another computer must be wss:// or https://. Loopback addresses may use ws:// or http://; a LAN address, a Docker alias or a Tailscale name does not count as loopback. A cleartext refusal sends no traffic and names the secure address. For a test hub on a cleartext port, UB_INSECURE_HUBS in the process environment lists exact host:port entries to allow; nothing stored on disk can supply that opt-in.

Agents and MCP entries

.mcp.json
{
  "mcpServers": {
    "uberblick": { "command": "ub", "args": ["mcp", "serve"] }
  }
}

ub mcp install registers a plain ub mcp serve with no workspace pinned, so every agent started in the project follows the file, and a use or promote moves all of them at once. A pin in the entry would silently keep agents on the old workspace after the file changes.

.mcp.json · one entry pinned to another workspace
{
  "mcpServers": {
    "uberblick": { "command": "ub", "args": ["mcp", "serve"] },
    "uberblick-design": {
      "command": "ub",
      "args": ["mcp", "serve"],
      "env": {
        "UB_WORKSPACE_ID": "uberblick-4f0b9c2e-7a1d-4e6b-9c35-8d2e1f6a0b47",
        "UB_HUB_URL": "wss://hub.example.com/ws"
      }
    }
  }
}

If one entry really needs another workspace, set UB_WORKSPACE_ID in that entry's env; it overrides the file for that entry only. Above, uberblick follows .uberblick.json while uberblick-design always serves the design workspace on the hub. UB_HUB_URL is only needed until this computer has that workspace. The agent then sees two servers with the same tools.

Browser and agents

The workspace switcher in the browser is for viewing. .uberblick.json decides where agents write; ub status shows which workspace that is.

Files on this computer

WhatWhere
Project binding.uberblick.json in the project, found by walking up from the current directory
Workspace copies~/.local/share/uberblick/<workspace-id>.sqlite, one per workspace, shared by every checkout on the computer
Logins and the local signing secret~/.config/uberblick/credentials.json, readable only by you, never copied into an MCP entry

XDG_CONFIG_HOME and XDG_DATA_HOME move the two directories; macOS uses the same dot directories, so a backup script works unchanged on both. Hub-side settings live in the hub's .env, see Run a hub.
