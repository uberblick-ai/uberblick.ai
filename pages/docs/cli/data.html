ub data

Charts and data tables draw from records a document owns. ub data moves those records through files, so a script produces them and an agent only reads the summary. Agents themselves use the MCP tools get_data and update_data.

Usage

help
$ ub data
usage: ub data [command]

commands:
  get <doc> [<collection>]       # Print the data summary, or one collection as JSON
  update <doc> --file <path|->   # Apply update_data operations from a file, or - for stdin

options:
  --out <file>                   # get: write the collection to this file instead of stdout
  --dry-run                      # update: validate and report, write nothing
  -h, --help                     # show this help

<doc> is a document id or link in the workspace this project is bound to.

get

Terminal
$ ub data get 7c1e4b2a-…
runs       42 records  valid
verdicts   40 records  valid
31,204 bytes
$ ub data get 7c1e4b2a-… runs --out runs.json
wrote runs: 42 records, 28,911 bytes → runs.json

Without a collection, the summary: each collection's record count and validity, and the size of the data area. With one, its schema and every record as {id, value}, as one JSON object on stdout or in the file named by --out. Invalid values are exported as stored. A document without data prints nothing and exits 0.

update

ops.json
[{ "collection": "runs", "upsert": [{ "id": "2026-10-09", "value": { "hours": 6.5 } }] }]
Terminal
$ ub data update 7c1e4b2a-… --file ops.json
runs       43 records (1 upserted)
saved; synced with hub
$ ub data update 7c1e4b2a-… --file ops.json --dry-run
runs       would be 43 records (1 upserted)
nothing written (dry run)

The file holds the same operations array update_data takes over MCP: set a schema, replace, delete or upsert records, validated as one batch. Each touched collection reports its resulting count and what changed; the same records again print no change. Nothing is written when any operation is refused. Same limits as MCP: 1 MiB of changes per update, 64 KiB per record or schema, 4 MiB per document. Archived documents and decision records refuse data writes. Unlike an MCP write, it does not require the guidance pages to have been read first.

Exit codes

0 for a successful read or update, including no change and a write saved locally that is not yet on the hub. 1 for a refused read or update or a failure to persist; 2 for a usage error. Refusals print the reason and nothing written on stderr; a get without --out writes only JSON to stdout.

Scenarios

A daily producer
./collect-runs.sh | ub data update 7c1e4b2a-… --file -. The script pipes its operations in; the chart on the report page is current in the morning, and the agent sees two lines instead of the records.
A bad record
error: runs/2026-10-09: Record /hours: expected type number, nothing written, exit 1. The whole batch is refused.
Offline
saved locally; not yet synced with hub, exit 0. It syncs the next time anything on this computer reaches the hub. It asks you to run ub auth login when one is needed.
Two writers
Last write wins per record. Writers touching different records both keep their changes; the same record is replaced whole, fields are not merged.
Check a generated file before it lands
--dry-run in the pipeline, the real run after. It works while ub open or an agent has the workspace open.
