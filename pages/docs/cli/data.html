ub data

Charts and data tables draw from records a document owns. ub data is the terminal side of that: a script exports a collection, a cron job or a CI step feeds new records in. Agents use the MCP tools instead.

Usage

help
usage: ub data [command]

commands:
  get <doc> [<collection>]       print the data summary, or one collection as JSON
  update <doc> --file <path|->   apply update_data operations from a file, or - for stdin

options:
  --out <file>                   get: write the collection to this file instead of stdout
  --dry-run                      update: validate and report, write nothing

get

Terminal
$ ub data get 7c1e… deliveries --out deliveries.json
wrote 42 records of deliveries to deliveries.json

Without a collection, the summary: every collection with its schema and record count, and what is invalid. With one, its records as JSON.

update

Terminal
$ ub data update 7c1e… --file ops.json --dry-run
$ ub data update 7c1e… --file - < ops.json
valid: 1 schema, 12 upserts, 0 deletes
applied: 12 upserts to deliveries

The file holds the same operations update_data takes over MCP: schema, replace, delete, upsert, validated as one batch. Nothing is written when any operation fails. --dry-run validates and reports. Exit 0 when applied, 1 when refused, 2 for a usage error. Offline, the write lands in the local copy and syncs later.

Scenarios

Nightly numbers
A cron job queries the warehouse, writes upserts and runs ub data update. The chart on the report page is current in the morning.
Take the numbers somewhere else
ub data get … --out, then whatever tool you like.
Check a generated file before it lands
--dry-run in the pipeline, the real run after.
