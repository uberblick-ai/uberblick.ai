Motivation

Uberblick, ub-agents and the small libraries beside them come from one team in Berlin that runs its own software with coding agents. None of them started as a product. Each was extracted from that work because something kept hurting. Good frameworks are extracted, not planned. This page says what hurt, once, so the other pages don't have to.

The premise

People and coding agents now work in the same codebase. Agents are only as good as the context they get: what the product should do, what was decided and why, what the numbers say. Most of that lives in local files and never gets shared. What is shared sits in tools that were not built for agents or MCP.

The same context has three readers: the agent building the change, the engineer running it, and the product manager who planned it. Each wants it in a different form. The agent wants a few exact blocks pulled into its context window and nothing else. The engineer wants to check at a glance what the agent read and what it wrote. The product manager wants to read, comment and decide. One shared workspace, with a native interface for each.

Our bet: one place for delivery, GitHub, and context that agents and people can both reach, each in the form that suits them. GitHub has the work. It lacks a home for the reasoning and the records. That is what we build, so a team can run on GitHub alone.

The pain

We started where everyone starts, with Markdown files in the repo. They went stale. Plans drafted in an agent session on one laptop died on that laptop. What agents wrote was often a wall of text. Then the files began to fill up every agent's context, and we caught ourselves writing index pages and a glossary so an agent could find its way through our own notes. That was the moment something felt wrong: we were building a wiki by hand, for machines.

Decisions hurt most. An agent that does not know a question was settled reopens it in code, with a plan and good arguments. We re-litigated the same choices every few weeks because the answer lived in a chat log on somebody's laptop. Numbers had the same problem: the report with the figures was a screenshot in a pull request, and the next report started from zero.

And every run starts cold. Agents have no memory, only what they are given, so the shape of what they are given decides the quality of the work. Giving them everything does not work; the context window fills with what does not matter. A short curated list that applies to everything, and the rest pulled by the change, does.

What we built

To make that work, we needed three things: a shared context store (Uberblick), an execution engine (ub-agents), and human-agent visual exchange formats (like ablauf & wireframe).

Uberblick is a workspace of documents that people and agents both edit. Think Notion meets Obsidian meets Jupyter: pages to write in, files you own, and data that is charted in place. It holds what the team must share and keep true: product intent, plans, reports, numbers, in blocks an agent can pick from when it goes to work, leaving the rest where it is. It is local first, synced via local SQLite and CRDTs, exposed to agents over a local MCP server and to people via a local web interface. It is easy to set up.

ub-agents is a loop engineering framework for GitHub: roles in a few lines of YAML, driven by labels, so issues get prepared, implemented, reviewed and merged by agents, with a person stepping in only where a label says so. Pairing with an agent should still be your default, especially for high-stake or high-ambiguity aspects. Everything else can simply be handed over to the loop. Each run ends with a short retrospective, and a few skills turn those into the next improvement. See agents.uberblick.ai.

ablauf and wireframe are small text formats for the things a team can only draw: how a flow runs and what a screen looks like. The agent writes a few lines of text and the person sees a drawing, where before they got a wall of text, or an artefact stored only on the machine of whoever was talking to the agent. The drawings live inside the document, next to the words, where the whole team sees them. See Diagrams and Wireframes.
