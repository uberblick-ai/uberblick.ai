Motivation

Uberblick, ub-agents and the small libraries beside them come from one team in Berlin that runs its own software with coding agents. None of them started as a product. Each was extracted from that work because something kept hurting. Good frameworks are extracted, not planned. This page says what hurt, once, so the other pages don't have to.

The pain

Like most teams, we tried to push agentic development forward: more throughput without dropping quality. Three questions came back in every project: how to handle product intent that spans repositories, how to keep Markdown current once agents write most of it, and how to bridge the language of product and design people with the language of the development team. And as agents wrote more of our code, our context shattered across Notion, Linear, Markdown files in half a dozen repositories and far too many ephemeral Claude Code artifacts, while a few individuals kept well maintained Obsidian vaults nobody else could reach.

We started where everyone starts: with Markdown in the repo. It went stale almost immediately. Plans drafted with an agent on one laptop died on that laptop. What agents wrote was often an impenetrable wall of text. Soon, files began filling up every agent's context window, and we caught ourselves writing manual index pages and glossaries just so an agent could navigate our own notes. We were building a wiki by hand, for machines.

Decisions hurt most. An agent that does not know a question was settled reopens it in code, with a fresh plan and good arguments. We re-litigated the same choices every few weeks because the rationale lived in a terminal chat log on somebody's machine. Numbers had the same problem: metrics lived as screenshots in pull requests, forcing every follow-up report to start from zero.

And every run starts cold. Agents have no memory, only the context they are fed. Stuffing the window with everything fails; a short, curated core that applies to the whole project, with the rest pulled on demand by the task, works.

What we built

To make that work, we needed three things: a shared context store (Uberblick), an execution engine (ub-agents), and human-agent visual formats (ablauf & wireframe).

Uberblick is a workspace of documents that people and agents both edit. Think Notion meets Obsidian meets Jupyter: pages to write in, local files you own, and data charted in place. It consolidates product intent, architecture decisions, plans and metrics into blocks an agent can query on demand. Because MCP round trips add up fast when an agent reads a dozen pages before writing a line, Uberblick is strictly local-first: built on SQLite and CRDTs, standing on the shoulders of Yjs and Hocuspocus, exposed to agents via a local MCP server and to people via a fast local web UI. Nothing in the cloud to start: one Homebrew formula.

ub-agents is a loop engineering framework for GitHub: roles defined in a few lines of YAML, driven by labels. Issues get scoped, implemented, reviewed and merged by agents, with humans stepping in only where an explicit label demands it. Pairing with an agent remains the default for high-ambiguity exploration; the loop handles the deterministic work downstream. Each run ends with a brief retrospective, and skills feed those learnings back into the next run. See agents.uberblick.ai.

ablauf & wireframe are text formats for the things teams need to draw: flows and screen layouts. Current diagram syntax often breaks inside LLM loops or looks unreadable in plain text diffs. With these libraries, an agent writes a few concise lines and the human sees a rendered diagram or wireframe directly inside the document, right next to the reasoning.

Build your own variant

None of this is meant as the single right answer. It is what held up under load for our team, published under the MIT license so you can take the parts that fit and replace the rest. The repositories are on GitHub.
