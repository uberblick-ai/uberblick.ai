Run a hub

A hub shares a workspace between computers and people. Every computer keeps its own copy and works offline; the hub passes changes on and admits only members. One hosted script starts and updates it, and ub-hub checks it from inside its container. This page is the reference; Set up a hub walks through a first hub for a team.

Agents: follow REMOTE.md for every by-hand procedure.

setup-hub.sh

help
$ HELP=1 /bin/bash -c "$(curl -fsSL https://uberblick.ai/setup-hub.sh)"
Start or update a Docker hub on this host.
Requires curl, Docker Engine 28.0.0+, Compose 2.24.4+, and Linux ss or macOS netstat.

  /bin/bash -c "$(curl -fsSL https://uberblick.ai/setup-hub.sh)"

Variables (put them before /bin/bash):
  HUB_HOST       Unset: loopback HTTP. Public DNS name: HTTPS on port 443.
                 A *.ts.net name: Tailscale HTTPS on Linux (Tailscale must be up).
  HUB_VERSION    Pin X.Y.Z; otherwise use GitHub's latest hub release.
  HUB_DIR        Deployment directory (default: ~/uberblick-remote).
  LOOPBACK_PORT  Loopback HTTP port (default: 8080).
  ALLOW_ROOT=1   Allow an explicit root run; Docker is never installed or updated.
  HELP=1         Print this help without checks or changes (also: --help).

Re-run to update or change the HTTPS hostname. Without route variables, an
existing .env keeps its route and other values. HTTPS-to-loopback switching,
release downgrades, Windows/WSL, Podman and rootless Docker are not supported.
  • Nothing is downloaded or changed until every check passes, and a failed check names what is missing and how to fix it.
  • It never calls sudo, never installs or updates Docker, and writes only inside HUB_DIR.
  • Running it again updates the hub and keeps its settings. Before it moves a running hub to another release it takes a backup, and it never moves a hub to an older release.
  • It ends with the hub's address and the ub auth login line that claims it.

Clients refuse an unencrypted hub on another computer, so there is no insecure mode to forget to turn off. To sign in with your own GitHub app instead of the shared one, see REMOTE.md.

The claim

A new hub has no administrator. The first GitHub account that signs in, with ub auth login hub.example.com from any computer or Sign in with GitHub in the browser, becomes hub admin and admin of the default workspace; the login warns before the approval. Nothing else can claim the hub afterwards, so claim it right after it is up. Further hub admins are appointed on the host with ub-hub hub-admin add. Members are GitHub logins, granted per workspace with ub workspace member; there are no Uberblick accounts.

ub-hub

help
$ docker compose exec hub ub-hub
usage: ub-hub <command>

commands:
  status                           Release, database and claim status
  doctor                           Diagnose this hub without changing it
  hub-admin add <github-login>     Appoint an account that has signed in
  hub-admin add --account-id <id>  Appoint by durable GitHub account ID
  backup                           Verify and save an online database copy
  restore [--yes] <file|->         Restore a database while the hub is stopped

Run it on the host, from HUB_DIR. status shows the release, the database and whether the hub is claimed; doctor checks the hub, database, storage, GitHub and clock and names the fix for each warning. backup prints the path of a copy to keep off the host; restoring one is in REMOTE.md. ub-hub never starts, stops or updates the hub.

Updating

Run the setup line again on the host. A release that changes the sync protocol needs the hub and every client updated in the same sitting: brew upgrade uberblick on each computer, then restart agents and ub open and reload browser tabs; until then clients report the mismatch and stay read-only. Stopping, rollback and recovery are in REMOTE.md.
