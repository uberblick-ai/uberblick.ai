Run a hub

A hub shares a workspace between computers and people. Every computer keeps its own copy and works offline; the hub passes changes on and admits only members. It is one Docker release, started and updated by one hosted script and operated with ub-hub inside its container. This page is the reference; Set up a hub walks through a first hub for a team, and REMOTE.md has what the script does by hand.

setup-hub.sh

usage
$ /bin/bash -c "$(curl -fsSL https://uberblick.ai/setup-hub.sh)"
$ HUB_HOST=<name> HUB_VERSION=X.Y.Z /bin/bash -c "$(curl -fsSL https://uberblick.ai/setup-hub.sh)"

HUB_HOST       The name other computers use: a public host name with port 443 open,
               or a Tailscale name (machine.tailnet.ts.net). Unset: this computer only
HUB_VERSION    Pin a hub release. Unset: the newest hub-vX.Y.Z release
HUB_DIR        Where the release files and .env live. Default ~/uberblick-remote
LOOPBACK_PORT  The local port when HUB_HOST is unset. Default 8080
ALLOW_ROOT=1   Allow running as root; the script never uses sudo
HELP=1         Print this and exit

Runs on the machine that hosts the hub: a Linux box with Docker Engine 28 or newer on x86_64, or a Mac with Docker Desktop for a hub that only your own computers use. It checks curl, Docker, Docker Compose and the ports before it downloads anything, and a failed check names what is missing and the command that fixes it. Then it fetches the four files of the release into HUB_DIR, writes a private .env (mode 600) with the release and the route, runs docker compose pull and up -d, and waits until ub-hub status reports a healthy hub. It ends with the next step: the hub's URL and the ub auth login line that claims it.

Running it again is the update and the route change: an existing .env keeps every value, HUB_VERSION moves to the newest release unless pinned, the route follows HUB_HOST when given, and the hub comes back on the new release after an ub-hub backup whose path is printed. The script never installs or updates Docker and changes nothing outside HUB_DIR.

Routes

RouteSetWhat listens
This computer onlynothinghttp://localhost:8080, published on 127.0.0.1 only; other computers cannot reach it
Public host nameHUB_HOST=hub.example.comhttps://hub.example.com, with a certificate the hub obtains itself; port 443 must be open and the name must resolve to the host
Tailscale, recommended for a teamHUB_HOST=machine.tailnet.ts.nethttps://machine.tailnet.ts.net on the tailnet address only, with the certificate from the host's Tailscale daemon; needs tailscale up on the host

Clients refuse an unencrypted hub on another computer, so there is no insecure mode to forget to turn off. In .env the routes are WEB_HOST, TAILSCALE_IP and COMPOSE_FILE; HUB_GITHUB_CLIENT_ID swaps the shared GitHub sign-in app for your own. The file comments every variable.

The claim

A new hub has no administrator. The first GitHub account that signs in, with ub auth login hub.example.com from any computer or Sign in with GitHub in the browser, becomes hub admin and admin of the default workspace; the login warns before the approval. Nothing else can claim the hub afterwards, so claim it right after it is up. Further hub admins are appointed on the host with ub-hub hub-admin add. Members are GitHub logins, granted per workspace with ub workspace member; there are no Uberblick accounts.

ub-hub

help
$ docker compose exec hub ub-hub
usage: ub-hub <command>

commands:
  status                           Release, database and claim status
  doctor                           Diagnose this hub without changing it
  hub-admin add <github-login>     Appoint an account that has signed in
  hub-admin add --account-id <id>  Appoint by durable GitHub account ID
  backup                           Verify and save an online database copy
  restore [--yes] <file|->         Restore a database while the hub is stopped

Run from HUB_DIR on the host, inside the container: docker compose exec hub ub-hub status. status shows the release, the database state and whether the hub is claimed; doctor checks hub, database, storage, GitHub and clock and names the fix for each warning. backup prints the path of a backup to copy off the host; to restore, stop the hub and run docker compose run --rm hub ub-hub restore <path>. Logs: docker compose logs --tail=100 hub caddy. Nothing here starts, stops or updates the containers.

Updating

Run the setup line again on the host. A release that changes the sync protocol needs the hub and every client updated in the same sitting: brew upgrade uberblick on each computer, then restart agents and ub open and reload browser tabs; until then clients report the mismatch and stay read-only. Documents and the claim live in named Docker volumes, so docker compose down and up -d keep them; only --volumes deletes them. Rollback and recovery are in REMOTE.md.

With Kamal

We use it with Kamal: the hub runs as an accessory next to the app.

If you replace the web image's Caddyfile with your own, keep admin 127.0.0.1:2019 in its global options and import /etc/caddy/uberblick-csp.caddy in the route that serves the app. REMOTE.md explains why.
