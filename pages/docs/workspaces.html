Workspaces

A workspace is one set of documents with its own sidebar, tags and members. Every computer that uses it keeps a full copy and works offline. A project directory is bound to one workspace by a small file, .uberblick.json, and everything in that directory, terminal commands and agents alike, follows the binding.

Create one

Terminal
$ ub workspace create "My Workspace"
created local workspace 3f0c… and selected it in ./.uberblick.json
$ ub open
Editor at http://127.0.0.1:7777 Keep this terminal open.

The workspace is local only and comes with a few starter documents. No hub, no login. What the two commands put on disk is in the guide Your first workspace. ub open serves the editor for the bound workspace until you stop it; --no-browser prints the address instead of opening one.

What the binding does

Commands and MCP servers look for the nearest .uberblick.json above the directory they start in. That is the whole selection mechanism: there is no current workspace on the machine, only the one a directory points at. Commit the file so everyone who clones the repository, and every agent that runs in it, lands in the same workspace.

.uberblick.json
{
  "workspaceId": "3f0c2a1e-…",
  "hubUrl": "https://hub.example.com"
}

Two environment variables, UB_WORKSPACE_ID and UB_HUB_URL, override the file for one shell or one agent process; see Configuration. A running agent keeps the workspace it started with, so restart it after changing the binding.

Join a shared one

Terminal
$ ub auth login https://hub.example.com
$ ub workspace use https://hub.example.com/3f0c2a1e-…
fetched 48 documents, verified, bound in ./.uberblick.json

ub workspace use takes a hub link with the workspace id as its last segment, or an id of a workspace this machine already has. It fetches the whole workspace, verifies that the copy matches the hub and only then writes the binding. It never starts a sign-in and never merges two workspaces. Someone has to have granted you access first: ub workspace member.

See what this machine has

Terminal
$ ub workspace list
3f0c2a1e-…  Uberblick product   https://hub.example.com
9b71d0c4-…  My Workspace

One row per copy: id, name and the hub it syncs with, blank for a local-only workspace. ub status says which of them the current directory is bound to and whether it is in sync.

Fork, promote, remove

  • ub workspace fork copies the bound workspace into an independent local one with a new id, including local changes and archived documents, and binds the directory to the copy. The source is untouched. Use it to try a restructuring without anyone seeing it.
  • ub workspace promote <hub> uploads a local-only workspace to a hub you administer, verifies the upload with a fresh client and then binds the project to the shared copy. Rerun it after an interruption; it resumes.
  • ub workspace remove <id> deletes this computer's copy and nothing else. The hub and the other computers keep theirs. MCP servers refuse to write to a removed workspace, so restart them.

Offline and sync

Every edit lands in the local copy first and is sent on when the hub is reachable, so a laptop on a train keeps working and catches up later. Two people editing the same block offline both keep their text; the document merges when they reconnect, block by block, and comments stay anchored. ub status shows the last full acknowledgement from the hub and names the fix when sync is refused: not signed in, no access, update required, or an unencrypted hub, which clients refuse unless it is on this machine.
