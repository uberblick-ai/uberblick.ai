Agents over MCP

Uberblick is built MCP first. The agent writes most of what is in a workspace: it searches, reads, edits block by block, keeps the data current and comments. The browser is where you review, adjust and settle what the agent should not decide. Register the server once with your agent's client and that is the whole setup.

Register the server

Run this in the project directory, with Claude Code or Codex installed:

Terminal
# Project scope, following ./.uberblick.json
$ ub mcp install claude

# Codex, or per-user instead of per-project
$ ub mcp install codex
$ ub mcp install claude --user

The command runs the client's own installer (claude mcp add, codex mcp add) and registers one server named uberblick that runs ub mcp serve. It never edits a config file itself. If an entry named uberblick already exists and is not ours, it is left alone and the snippet is printed instead. Restart the client, or reload its MCP servers, after installing.

For a client the command does not know, ub mcp install cursor --print prints the snippet and does nothing else.

Which workspace the agent sees

The server follows the nearest .uberblick.json above the directory the client started in, the same binding the terminal commands use. Agents never choose a workspace; they inherit the project's selection. Restart a running agent after you change the binding, because it keeps the workspace it started with.

A session can use several workspaces through separately named entries in the client's own config, each with its own UB_WORKSPACE_ID and UB_HUB_URL; see Project binding.

Agent instructions

The server does not decide how an agent should behave; your instructions do. This is the workspace section of our own AGENTS.md. Copy it, then cut what your team does not need. Each tool carries its contract in its own description and get_help returns the product help, so the instructions need no tool list.

AGENTS.md · the workspace section
## The workspace (Uberblick over MCP)

- Product intent lives in the workspace, not in this repository. Start from the
  documents pinned in the sidebar (get_sidebar) when you do not know the project.
- Discover documents with list_docs and search; use list_tags for current tag
  names before filtering by tag. Decisions are listed only with kind: decision.
- Cite pages by title and id, discovered at runtime. Never pin an id in a
  reusable instruction. An id the workspace no longer has is a stale pointer:
  find the live successor by search and note the replacement.
- Before a product-sensitive choice, call find_decisions for the issue you work
  on and read what comes back. Do not reopen a decided question in code.
- Edit the block that is wrong with edit_block. Do not replace a page to change
  a sentence. Never delete and reinsert a block to change its type.
- Pages describe intended behaviour, which may be ahead of the code. Update the
  owning page in the pull request: which page, which block, what it now says.
- Do not load the whole workspace. Read what the change touches.

Why each line is there

  • Start from the sidebar. The sidebar is curated by people. An agent that starts from search alone finds the most recent page, not the most important one.
  • Cite by id, discovered at runtime. Titles change and pages get superseded. An instruction file with ids in it rots in a week; a runtime lookup does not.
  • Decisions by issue. The decision that governs an issue is linked from the record, so find_decisions is one call and needs no memory of last month.
  • Edit the block. Replacing a page destroys comment anchors and the history of every other block. The server keeps block ids stable for exactly this reason.
  • Update the page in the PR. This is the line that keeps the workspace true. A reviewer checks the corpus update like any other part of the diff.
  • Do not load everything. Context is finite. The guidance pages are named when the server starts; the rest should be pulled by the change.

Who does what

Nothing in Uberblick starts an agent. A comment in the browser waits for a person, or for the next agent run that reads the page. A run starts where it always did: in your terminal, or in a loop you set up, such as ub-agents picking up a labelled issue.

WhoDoes
UberblickStores the pages, decisions, comments and records, and serves them over MCP and in the browser.
Your coding agentReads and edits over MCP while it runs, following the instructions above.
Your teamWrites the pages, comments on edits, settles decisions, reviews the pull request.
ub-agents, optionalStarts runs from issue labels on GitHub and gathers the delivery numbers; without it you start every run yourself.

With ub-agents

In the ub-agents loop the same rules apply to each role with one addition each. The preparer scans the workspace and puts the links an implementer will need into the issue. The implementer builds against the pages and writes the corpus update. The reviewer checks the result against the pages, not against the issue text. The retrospective may propose a change to the pages or to these rules; a person decides. If you follow the harness engineering and loop engineering discussions: this is that, with a person deciding each change. How that looks in practice is on Product intent that agents read before they build.
